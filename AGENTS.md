# AGENTS.md

Instructions for AI coding agents (Copilot, Claude Code, Codex and others) working in this repo, and for the people using them. Read README.md and CONTRIBUTING.md too.

## What this repo is

The LITSA course planner, served at suffolklitsa.org/planner. Plain HTML, CSS and JavaScript modules in `web/`, a Python importer in `scripts/`, and the course data in `data/courses.json`.

## Commands

```
python3 -m unittest discover -s tests     # importer tests
node --test web/*.test.js                 # scheduling logic tests
python3 scripts/validate_data.py          # courses.json matches docs/DATA.md
npx playwright test                       # browser tests (npm ci first)
python3 scripts/build_site.py && python3 -m http.server 8000 -d dist   # run it
```

## Rules for this repo

- **Branches:** work from `staging` and open pull requests against it. Never target `main`; maintainers promote `staging` to `main`.
- **Never edit `data/courses.json` by hand.** It's generated by `scripts/import_offerings.py`. Data problems become issues.
- **Logic goes in `web/planner.js`,** with no `document`, `window` or `localStorage` there, and every new function gets a test in `web/planner.test.js`.
- **No dependencies, no frameworks, no build step,** unless the issue says so.
- **A student's plan never leaves the browser.** The only network calls are loading `courses.json` and the site's own cookieless analytics (page views and the anonymous usage counts listed in the README). Never send search text, plan contents, year or division, share links or any identifier. No third-party scripts.
- **Changing the data shape** means updating `docs/DATA.md`, `scripts/validate_data.py`, the importer and its tests in the same pull request.
- **Requirement rules** (what counts toward the writing requirement, experiential credit and so on) need a linked Suffolk source and the `needs R&W review` label.
- Keep the page usable by keyboard and at 390px wide.

## Rules for every LITSA repo

- **No secrets.** Never write API keys, tokens or passwords into a file, a commit, an issue or a test. Keys come from environment variables. If you find one committed, stop and tell a maintainer.
- **No personal data.** No real names, emails, student records, sign-in sheets or mailing lists in code, tests, fixtures, screenshots or commit messages. Use made-up examples (`jane.doe@example.edu`).
- **No invented law.** Anything stating a rule, statute, case or requirement must come from a source you can link. Never make up a citation. If you can't find the source, say so in the pull request instead of guessing.
- **Small changes.** One issue per pull request. Don't reformat or rename things the issue didn't ask about.
- **Run the checks** listed above before saying the work is done, and report what they printed. If one fails, fix it or say plainly that it fails.
- **Plain writing.** Docs and messages use short, ordinary sentences a first-year law student would follow.
- **Disclose AI use.** The person opening the pull request notes which AI tools helped, in the description. They own every line either way.
